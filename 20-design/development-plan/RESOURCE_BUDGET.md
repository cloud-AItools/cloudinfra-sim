## 5. 규모 벤치마크와 목표 (Phase 5, NFR-0115 ~ NFR-0117, WP 5.6·5.9)

측정: 2026-10-11, Windows 11 개발 PC 1대, full 실행 프로필, 실행파일을 별도 프로세스로 띄우고(`40-test/performance`, `make perf`) 혼합 요청(REST VM 전체 목록·VM 조회, NSX Segment 조회·Tier-1 목록·Segment 쓰기 = 각 1/5)을 5초간 보냈다. 원자료: `40-test/performance/results/`. NFR-0116의 규모 값은 검증 시나리오이며 보장 처리량이 아니다(NFR-0117).

| 규모 | 기동 | 유휴 메모리 | 동시 10: req/s · p95 | 동시 50 | 동시 100 | 개선 전(동시 10) |
|---|---|---|---|---|---|---|
| VM 100·Segment 10 | 4.8초 | 103 MB | 1,104 · 41 ms | 760 req/s · 293 ms | 664 req/s · 639 ms | 92 req/s · 520 ms |
| VM 1,000·Segment 10 | 42초 | 188 MB | 267 · 174 ms | 230 req/s · 958 ms | 209 req/s · 2.4초 | 10 req/s · 5.3초 |
| VM 20·Segment 1,000 | 15초 | 145 MB | 282 · 165 ms | 216 req/s · 1.1초 | 203 req/s · 2.6초 | 20 req/s · 2.8초 |
| VM 5,000·Segment 10 | 210초 | 466 MB | 49 · 0.99초 | 49 req/s · 5.0초 | 50 req/s · 9.6초, 최대 872 MB | 2 req/s · 18.8초, 동시 50부터 60초 Timeout |

p95는 혼합 요청 전체 기준이며 대부분 Segment 쓰기(교차 락 직렬화)에서 나온다. 읽기 p95는 VM 1,000개·동시 50에서 90 ms 이하. 개선 후 HTTP 오류·Timeout 0건. 전송 계층 TLS alert(`bad record MAC`)가 VM 5,000·동시 50에서 1건(465건 중) 다시 나타났다(R-45 ③, 원인 미확인).

**해석:** R-45 증분 관계 조정(2026-10-11) 뒤 Segment 쓰기 1건의 관계 조정이 VM 1,000개 기준 255 ms → 16 ms, Segment 1,000개 기준 89 ms → 13 ms가 됐다. 쓰기는 여전히 교차 락으로 직렬화되므로 동시성이 늘면 대기 지연이 늘지만 Timeout은 사라졌다. 기동 시간은 vcsim의 VM 생성(VM당 약 42 ms, Windows 파일 생성)에 비례한다. 위 표의 기동은 캐시 없이 측정한 값이다(벤치마크 기본 `--fixture-cache off`). **R-45 ② Fixture 캐시(2026-10-11, DEVELOPMENT_PLAN §13.5):** 같은 Fixture로 다시 기동하거나 Reset하면 VM 1,000개 16.9초, 2,000개 16.7 ~ 37초, 5,000개 43 ~ 60초(첫 기동은 저장 포함 62.8 / 120 / 262초). 캐시는 데이터 디렉터리에 VM 2,000개 기준 약 74 MB, 최근 2개 유지.

**목표(NFR-0117 결정 — Phase 5 측정 기준, 2026-10-11 사용자 승인):** full 프로필에서 VM·Segment 1,000개 이하, 동시 50 이하일 때 HTTP 오류·Timeout 0, 전송 계층 오류 0.1% 이하(벤치마크 회귀 기준). VM 5,000·동시 100은 측정만 하고 보장하지 않는다. 기본 예산(NFR-0109 ~ 0112, default-small·lite)은 벤치마크와 무관하게 유지한다.

**보존 수렴(WP 5.9, `make soak`, 개선 후):** full, 보존 한도 축소(Trace 2,000건·8 MB, 전이·작업 2,000건), 동시 20 × 15초 × 6단계, 누적 71,323 요청(개선 전 25,097): 메모리 141 → 153 → 163 → 169 → 175 → 184 MB, DB 8.5 → 10.4 MB. 마지막 두 단계 차이 5.1%로 판정 기준(15%) 이내이나 단계마다 5% 안팎 늘어 평탄해지지 않았다(R-45 ④). 24시간 운전은 하지 않았다.

**R-45 ④ 수정 후(2026-10-11, DEVELOPMENT_PLAN §13.4):** 같은 조건 6단계, 누적 52,032 요청: 메모리 139.8 → 138.6 → 139.5 → 141.1 → 137.5 → 138.7 MB(단계 간 ±2%), DB 8.9 → 10.7 MB. 원인이던 유휴 keep-alive 연결(Gateway `IdleTimeout` 2분)과 vcsim 세션 객체 락 누수를 고쳤다. 10단계 pprof 측정에서 GC 뒤 Go 힙 20.5 → 21.8 MB, 고루틴 105 → 91. 절대값(110 ~ 140 MB)은 실행마다 Windows 작업 집합 차이로 달라진다.

**측정 중 고친 결함:** full 프로필이 Trace 링버퍼를 한도(1,000,000건) 크기로 미리 잡아 유휴 메모리가 약 180 MB 늘던 문제(268 → 83 MB), full DB의 요청마다 fsync(synchronous=FULL)로 처리량이 묶이던 문제(NORMAL로 변경), 관계 입력이 아닌 NSX 쓰기(Group·Service·Tier-1 등)도 관계 조정을 돌리던 문제(쓰기 50 ms → 1 ms, VM 100개 기준).
